# 部署与第一次使用

[返回首页](../README.md) · [运行与备份](maintenance.md) · [排障](troubleshooting.md)

## 部署前准备

需要 Docker Engine/Desktop、Linux 容器模式、Docker Compose v2.20+ 和可执行 `sh` 的终端。Windows 用户可在 WSL 中运行。当前完整部署验证的容器平台为 **Linux ARM64**；amd64 尚未完成整套验证，不能据多架构基础镜像推定全栈已验证。

为 Milvus 预留至少 8 GiB 内存，整套环境还需额外的应用、CPU 推理与编译空间。磁盘需容纳基础镜像、原生编译缓存、模型权重和业务卷；尚无跨机器实测的统一容量或构建时长承诺。Docker Desktop 用户应先在资源设置中分配足够内存及磁盘。

首次构建需要访问镜像仓库、GitHub、Go 模块源、npm、PyTorch/Hugging Face 和小米字体 CDN，下载固定版本依赖、BGE 模型及官方字体分片，并编译媒体和检索组件。无需在本机安装 Go、Node.js、Python 或手工准备字体、配置文件和数据库。

## 启动

下载源码 ZIP 并解压，在包含 `deploy.sh` 的源码根目录打开终端，执行：

```sh
sh deploy.sh
```

脚本检查 Docker、Compose 版本和 Docker 服务，构建并启动整套环境，等待健康后打印访问入口。首次构建可能较久；600 秒是构建之后的健康等待时间，不是首次构建总耗时。失败时先按[排障指南](troubleshooting.md)检查，修复后再次运行同一命令。

| 入口 | 地址或凭据 |
| --- | --- |
| 创作工作台 | <http://127.0.0.1:8787/demo/app/> |
| 运营后台 | <http://127.0.0.1:8787/demo/app/#/operations-login> |
| 初始化用户名 | `Daydream` |
| 初始化密码 | `Daydream123456` |

两个入口可使用同一个初始运营账号，无需先注册新用户；两个入口的登录会话独立。默认仅绑定本机回环地址，应用端口为 `8787`，PostgreSQL 客户端端口为 `55432`。Compose 使用固定容器名，同机直接启动第二套会发生冲突，单独更改项目名不足以实现并行部署。对外提供访问时，部署者需自行配置域名、HTTPS、访问控制及适用的服务条款。

## 第一次使用

1. 登录后打开头像中的账号设置，修改公开的初始化密码。初始账号使用不可投递的占位邮箱，不要依赖邮件找回密码。
2. 在运营后台配置自己的**分析模型**连接和 API Key，检查上下文容量、最大输出和厂商计费配置，启用需要使用的模型并保存。没有可用分析模型时，剧本分析不会开始。
3. 设置该模型的站内积分价格。使用正价模型时，为使用账号分配足够积分；零价或有效限免按规则执行。站内积分与厂商真实账单分别计算，限免不代表厂商免费。
4. 回到工作台创建项目、选择已启用的分析模型、导入剧本，再明确点击开始。图片和视频任务目前请选择本地 Mock；它们不需要真实媒体厂商密钥。
5. 需要多人注册、验证码或邮件功能时，再配置 SMTP 和注册设置。单人用初始化账号体验工作台不要求先配置邮件。

已有 DeepSeek、OpenAI Chat 兼容协议、火山引擎和 Google 文本适配；协议兼容性以实际模型为准。图片和视频目前只有本地免费 Mock，用于体验任务提交、状态和结果流程；页面中的厂商预设不代表已经支持真实图片或视频生成。

新部署不附带供应商凭据，不会因启动或配置连接而自动生成付费内容；明确发起文本分析等操作可能产生供应商费用。

## 初始化与持久化

Compose 自动生成私有基础设施凭据，并在空数据库创建基础设置和这一个运营账号。[初始化 SQL](../deploy/init.sql) 从代码中的表结构和种子生成，不包含开发者账号、项目、上传、用量、邮件或业务流水。数据库已有任何用户时不再添加公开初始化账号，重复运行部署脚本不重置已有密码或业务数据，也不删除数据卷。

系统由两个应用镜像组成：后端镜像 `daydream-backend` 包含 API、任务 worker、本地 BGE CPU 推理和媒体工具；前端镜像 `daydream-frontend` 用 nginx 提供工作台页面，并把 `/api/` 转发给后端。浏览器只访问前端发布的 `8787` 端口，后端不向宿主机发布端口。配套服务为 PostgreSQL 17、Redis 8、Milvus 3.0.3、NSQ 1.3.0 和 [PGSTY Silo](https://github.com/pgsty/silo) S3 对象存储。Milvus 与 NSQ 的 Go 程序使用 Go 1.26.10 和独立依赖锁重建，Milvus 原生库保持同一上游版本。

基础设施原凭据保存在 `runtime-config` 卷，模型/SMTP 原加密密钥保存在 `app-data` 卷；业务数据使用独立卷。请按[维护指南](maintenance.md#备份与恢复)配套备份，不用删卷处理启动问题。

## 高级部署

以下均为可选操作；普通部署只需上面的一条命令。所有命令在源码根目录执行。

### 直接使用 Compose

部署脚本调用整套 Compose 构建、重建和健康等待；也可直接执行同等操作：

```sh
docker compose up --build --force-recreate -d --wait --wait-timeout 600
```

backend 已内置任务 worker。如需额外 worker，可选择启用，不对固定容器名使用 `--scale`：

```sh
sh deploy.sh --profile workers
```

脚本支持在 `sh deploy.sh` 后传入 Compose 全局参数，例如 `--profile workers`、`-p` 项目名或 `-f` 覆盖文件。脚本始终先切换到源码根目录，`-f` 的相对路径也按该目录解释；需要时使用绝对路径。使用自定义参数时，后续启动、更新、备份和恢复都要沿用同一组参数，并核对卷名。NSQ、Milvus 和额外 worker 共用 backend 的网络命名空间，更新时须一起重建，详见[维护指南](maintenance.md#运行与更新)。

### 自建空库

仅当使用自己的 **PostgreSQL 17 空库**、并已设置好本机私有连接变量时，可手工导入 SQL：

```sh
psql "$DATABASE_URL" -v ON_ERROR_STOP=1 -f deploy/init.sql
```

配置格式可参考 [config/app.example.yaml](../config/app.example.yaml)，样例中的密码不是 Compose 生成的实际密码。独立运行时需要自行配置配套服务，私有配置使用 `config/app.local.yaml`、文件权限设为 0600；模型、SMTP 和注册设置由运营后台管理。
